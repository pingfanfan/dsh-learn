# 正文

DeepSeek Harness 官方 Discussions 的 #37、#38 和 #40，表面上都像是页面出了问题，实际落在三个不同位置。#37 是 Windows 11 和 Firefox 的原生目录选择窗口跑到了浏览器后面，#38 是 Windows 目录选择器找不到 `koffi`，#40 是会话归档后没有查看和恢复入口。

这三条帖子很适合放进完全新手的排障入口，因为它们展示了同一个感觉是怎样被拆开的。浏览器窗口、DSH 进程里的原生依赖、Workspace 和 Session 的界面记录，分别要看不同的回执，不能只凭页面上一个按钮没有反应，就把原因归到 DSH、Node.js 或模型身上。

## #37 先看浏览器窗口和本机 host

#37 的环境写得比较清楚，Windows 11、Firefox 153.0esr、`@deepseek-ai/dsh@0.1.0-rc.6`，通过 `dsh web` 打开 Web UI，点击添加工作区以后，原生文件夹选择对话框出现在浏览器窗口后面，任务栏会闪烁，用户需要手动切换过去才能操作。同一环境换 Brave 测试时，作者报告窗口可以正常出现在前面。

这条记录支持的判断很窄，它说明一次浏览器和桌面窗口交互异常，不足以推出 Firefox 与 DSH 存在统一兼容性问题，也不足以把 Brave 写成官方解决办法。新手看到添加工作区按钮没有反应时，可以同时看浏览器地址、任务栏、运行 DSH 的终端和本机是否出现文件夹选择窗口，四个位置提供的信息不一样。

截图在这里只能证明某一刻的画面。带地址栏的浏览器截图可以确认连接到了哪个 Web UI，任务栏或窗口切换画面可以说明原生窗口可能被遮住，终端回执才能帮助别人知道 `dsh web` 运行在哪个系统和目录，缺少其中一项时，别人很难判断是窗口层级、浏览器行为还是 host 没有发起选择流程。

如果换浏览器后现象消失，也只是在当前机器和当前版本下多了一条对照线。它有助于上游缩小范围，却不是换浏览器就修好的教程，发帖时还应该留下 Firefox 版本、系统版本、DSH 版本、启动方式和点击动作。

## #38 的 `koffi` 报错属于依赖加载层

#38 的错误信息显示，`@deepseek-ai/dsh-host-directory-picker-native` 在运行目录选择器时，找不到 `koffi` 的 `index.js`，路径还包含 Node.js、DSH 和 Windows 安装目录。评论里有人指出这看起来像 Node.js 模块加载失败，也有人提醒它和 #30 的目录选择错误相似，但这些都是讨论中的线索，不是维护者确认的修复方案。

这类错误和 #37 不在同一层。#37 的目录选择窗口已经出现，只是窗口位置不合适，#38 则是原生目录选择器还没有完成依赖加载，程序没有走到同一个界面阶段。把两条帖子合并成 Windows 文件夹选择坏了，会让复现条件和上游定位都变得模糊。

遇到类似错误时，保留 DSH 精确版本、Node.js 版本、操作系统、包管理器、安装方式和第一段错误，路径中的用户名、项目目录、内部域名和完整日志要先脱敏。不要看到 `koffi` 就从网上随便复制一个安装命令，也不要把评论中的初步判断写成补装某个包即可解决，因为依赖树、安装方式和 Node.js 版本都可能改变结果。

对完全新手而言，最有用的动作是把安装是否完成和目录选择器是否可用分开记录，`dsh --version` 能证明命令版本，启动 Web UI 能证明服务尝试运行，点击工作区按钮出现 `directory picker failed` 才说明问题走到了目录选择器，三种结果不要合成一句 DSH 安装失败。

如果要向官方提交新问题，最短复现应该包含运行命令、操作步骤、预期结果和实际结果，公共帖子里不放 API Key、Cookie、Authorization header、私有路径和整段内部日志。错误信息足够长时，截取能说明模块名和错误类型的部分就够了。

## #40 的限制在 Session 和 Workspace 记录里

#40 的正文只有一句求助，意思是会话归档以后，在设置里找不到已经归档的历史会话，评论里有用户表示同样无法重新浏览，也有人引用官方固定 commit 的 `packages/client/ui-workspace/README.zh.md` 已知限制。该文档明确写着当前没有 Session 删除与取消归档控件，已归档会话没有查看或取消归档入口，删除 Workspace 注册记录也不会删除 Session。

这条代码文档能够支撑的是当前界面边界，不是一个隐藏恢复命令，也不是 Session 已经丢失的证明。新手把会话归档以后找不到它，应该保存归档前后的 Workspace 名称、Session 标题、操作时间和 DSH 版本，不要为了恢复而删除 Workspace 注册记录，那个动作不会替你删除或找回 Session。

这里还要把归档和删除分开。归档通常改变的是会话在列表中的显示状态，删除 Workspace 注册信息属于另一种管理动作，固定 commit 的 README 已经把两者的边界写出来了。没有恢复入口时，教程应该如实写成当前限制，等上游提供新控件或新文档以后再重新核对。

归档以后找不到会话，最容易出现的误会是把列表里看不见理解成数据已经消失，但当前界面是否提供查看入口，和底层 Session 是否还在，是两个需要分别确认的问题，教程不能用一个动作替用户补出恢复结果。

## dsh-learn 的新手分流方式

第一次启动 DSH 的人，可以沿着固定的 rc.6 无 Key 入口完成命令版本、Web UI、本机端口、工作区和 hello-plugin 的本地验证，截图用于说明浏览器画面，终端回执用于说明启动命令和错误，配置导出用于说明 profile 和 bundle，模型请求单独放到后面的验证阶段。

遇到 #37 类型的现象，记录浏览器和本机窗口，遇到 #38 类型的现象，记录依赖和安装方式，遇到 #40 类型的现象，记录 Workspace、Session 和归档操作。问题虽然都来自 DSH Web UI，却不应该共用一份重装 Node.js 或换浏览器的万能清单。

完全新手还可以给每一次尝试保留一个小回执，里面写命令、时间、浏览器地址、工作区名称和屏幕上看到的结果，失败时再加上终端第一段错误，这比只写一句打不开更容易让别人复查，也能避免第二次操作把第一次现场覆盖掉。

没有 API Key 时，仍然可以完成命令版本、Web 页面、端口、临时 profile 和无 Key 插件的本地检查，这些检查不会证明模型回复，也不会证明第三方渠道已经连通，但能把安装层和模型层分开，教程截图也应该把这条边界写在图旁边。

如果页面看起来已经启动，工作区却没有出现，可以对照浏览器连接的地址和启动 DSH 的终端是否属于同一台机器，随后查看工作区路径来自哪一个本机选择器，再把错误和操作时间对应起来，别把页面加载成功当成文件操作成功。

如果归档会话暂时找不到，教程可以教用户保存标题和时间，说明当前界面没有恢复入口，等官方文档或代码出现新变化后再复测，不能为了让教程看起来完整，就给出没有证据的目录搜索、数据库修改或文件复制方法。

这类排障卡还应该告诉读者什么时候停止尝试，窗口层级问题可以补充浏览器对照，依赖加载问题需要保留安装环境，归档限制则应该等待界面或文档变化，三种情况都不适合用反复重装来替代证据。

一张适合新手的截图也不必把所有终端内容都塞进去，地址栏、版本、错误短句和当前按钮状态已经能承担一部分定位工作，完整命令和脱敏后的回执放在文字里，读者才有机会照着复查而不是只看一张无法操作的图片。

提交 Discussion 时，环境、最小复现、错误边界和隐私脱敏都写在帖子里，别人才能判断这是一条浏览器对照、依赖加载、界面限制还是尚未确认的功能需求。用户评论可以帮助发现重复现象，不能自动变成维护者结论。
