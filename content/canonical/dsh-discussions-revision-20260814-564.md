# 正文

DeepSeek Harness 的新手教程，不能只写先复制命令再打开网页，常常让人卡住的地方是网页已经打开，工作区却创建失败，或者模型已经加进列表，第一次请求却返回 400。

这张卡只谈官方 Discussions #560–#564 这组历史线索，它们在 2026 年 8 月 14 日最初复核时位于第 6 页，公开列表共 550 条，最后编号为 #564。现在列表已经扩展到第 7 页、696 条，最后编号为 #714，但后来的讨论不混入这张卡的历史结论，新手仍然要把路径问题和模型网关问题分开，看清社区报告、官方源码和本地动态结果各自能证明什么。

## 网页能打开以后

如果你第一次启动 DSH，先按新手入口里的固定版本命令运行

```bash
npx --yes @deepseek-ai/dsh@0.1.0-rc.6 web
```

浏览器能打开本机 3080 端口，只说明 Web UI 进程已经起来，页面里还要继续添加工作区。Windows 用户若在这一步遇到路径不存在、路径截断或工作区创建失败，最近的 Discussion #563 提供了一条值得记录的线索。

报告描述的是 Windows 原生文件夹选择器，用户选择了桌面下的安卓开发目录，错误信息却只剩下安卓两个字，作者认为目录选择器里的 `readUtf16` 只检查 UTF-16 码元的低字节，可能把某些中文字符误认成字符串结束。

我把报告给出的函数和官方固定 commit 中的同名实现做了静态对照，两者代码形状一致，这足以说明报告指向了真实源码位置，但不能证明 dsh-learn 已在 Windows 实机重现，也不能证明修复已经进入官方版本。

新手可以先把练习目录放在短的 ASCII 路径，例如 `dsh\\demo`，再重新选择工作区，这只是临时绕开中文路径变量，其他 Windows 路径问题仍需单独判断。macOS 或 Linux 用户不应把这条 Windows 报告自动套到自己的报错上。

## 模型添加以后

另一类现象是模型已经出现在列表里，思考强度似乎也能选择，但发送请求就返回 400，尤其是第三方 OpenAI-compatible 网关接入模型时，接口形状相似并不代表每个字段和角色都能被接受。

Discussion #564 展示了一套社区实现，目标就是处理网关方言差异，作者让适配器在添加模型时做最小能力探测，再把兼容事实放到按主机名匹配的预设里。社区仓库 `dsh-gateway-presets` 已经可以访问，包版本为 `0.1.0`，还提供了 PowerShell 探测脚本。

这里有一条新手必须知道的边界，这个预设服务只有在能消费它的 DSH 构建里才会生效，仓库 README 明确说明原版上游构建不会消费该服务，目前使用目标是作者自己的增强 fork。因此，在官方 `@deepseek-ai/dsh@0.1.0-rc.6` 里安装这个社区包，不应被当作官方版本已经拥有网关兼容层。

本轮只检查了仓库、README、package manifest、探测脚本和 fork 分支的静态内容，没有下载 fork，没有构建，没有安装插件，也没有调用火山方舟或其他模型 API。作者写在 Discussion 里的两个网关结果属于作者提供的实测陈述，不能替代 dsh-learn 的独立回执。

遇到第三方网关 400，可以按这个顺序处理

1. 确认 DSH 版本、模型名、接口地址和凭据属于同一个配置层。
2. 查看 400 指向角色、推理参数还是输出长度字段。
3. 不要因模型列表能返回，就判断聊天请求的完整协议兼容。
4. 只有明确接受独立构建和回滚成本时，才考虑社区 fork。

第一次学习 DSH 时，建议先使用已经工作的官方 provider，完成 Web UI、工作区和无 Key 插件实验，再处理第三方网关。Node.js、路径、provider、模型名和网关方言同时出问题时，排查会变得非常困难。

## 把报错放回正确的层次

新手遇到错误时，先记下 DSH 版本、Node.js 版本、运行命令所在目录和完整错误原文，这四项信息比一张裁掉上下文的截图更有用。命令窗口不要马上关闭，网页也先保留当前页面，后面需要确认进程是否还在运行。

如果错误发生在浏览器打开之前，先看 Node.js、`npx`、网络和端口，如果网页能打开但工作区创建失败，优先看目录选择器、路径长度和权限，如果工作区正常但模型请求失败，再看 provider、模型名、接口地址和网关字段。插件安装问题则要单独记录 profile、bundle、包名和加载日志，不要用模型请求失败来判断插件是否安装成功。

排障时每次只改变一个变量，例如先换成短路径，重新测试后再换 provider，这样才能知道哪一个动作改变了结果。若一个社区建议需要切换 fork、重新构建或填写新的凭据，就先保存官方版本的可用状态，并把回滚方式写在旁边，避免为了验证一个猜想把基础环境一起改掉。

## 图片输入的另一层限制

Discussion #561 提出，当模型的 `inputModalities` 没有声明 `image` 时，是否可以增加设置，让 DSH 继续把图片发给模型，再由自定义视觉流程处理，这个建议有实际背景，但当前还没有成为可用设置。

讨论中引用的官方代码会在模型明确不支持图片时返回 `MODEL_DOES_NOT_SUPPORT_IMAGES`，新手看到这个错误，先换用支持图片的模型或移除图片更稳妥，不要在配置文件里猜一个尚未实现的开关。

网页显示图片选择按钮，只能说明前端允许选择附件，模型是否接受、provider 是否转发、网关是否保留图片内容，还要看后面的模型能力声明和接口协议。

## 截图和性能数字

Discussion #560 是一张缓存命中率展示图，作者说自己测试了一整晚并观察到很高的命中率，这对理解使用体验有帮助，但单张截图不能推出所有模型、会话和 provider 都有同样结果，还应同时确认统计时间、模型版本、会话规模、请求数量、缓存策略和是否存在预热过程，任何一项不同都可能改变数字的含义。

Discussion #562 是一份真实协作反馈工作单，谈到搜索工具、并行分身、通知去重、进度可见性和沙箱删除边界，这些反馈对生态有价值，但它们仍然是用户提交的工作单，不能当作官方已经接受，也不能当作 dsh-learn 在相同环境中的复现。

新手读 DSH 内容时，可以把证据分成三层

- 官方源码或文档，证明某个版本有什么代码或说明
- 社区报告，证明有人遇到了某个现象或提出了某个建议
- 本地动态复现，证明我们的环境确实跑出了某个结果

三层证据可以同时存在，插件也应逐层观察，仓库存在、README 有安装命令、npm 包能下载、插件被 profile 加载、插件参与模型调用，是五个不同事实。

## 完全新手的最短路径

如果目标只是先把 DSH 跑起来，按下面顺序会更省力

1. 安装满足要求的 Node.js。
2. 用固定版本命令启动 DSH Web UI。
3. 第一次看到 API Key 提示时选择 `Configure later`。
4. 在无 Key 隔离实验里完成第一个插件的安装、加载和移除。
5. Windows 用户先把练习目录放到短的 ASCII 路径。
6. 等官方 provider 和基础插件路径稳定后，再尝试第三方网关。

这条路径的价值，在于每一层都单独回答一个问题，Node.js 能否执行，DSH 能否启动，网页能否加载，工作区能否创建，插件能否加载，模型请求是否兼容。

DSH 仍处于 Developer Preview 阶段，当前最有用的教程，是把新手可能遇到的现象、证据等级和下一步动作写清楚，不把社区线索写成已经解决，这样版本变化时教程也更容易维护。
