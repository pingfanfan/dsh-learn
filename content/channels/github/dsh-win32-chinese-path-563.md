# Windows 中文路径被截断，DSH 工作区为什么创建失败

在 Windows 上用 DSH 的 Web 界面添加工作区时，你可能会遇到一种很容易误判的错误，文件夹明明刚刚在系统对话框里选中，DSH 却说这条路径不存在。

官方 Discussions 的一条报告给出了很具体的例子，用户选择的是 C 盘下的 `Users\\XIAOPAN\\Desktop\\安卓开发`，工作区创建失败时，错误里的路径只剩下了 `Users\\XIAOPAN\\Desktop\\安卓`，后面的开发不见了。这个现象可以从两处排除，文件夹没有突然被删除，DSH 也没有把工作区目录改到别处，原生 Windows 目录选择器把路径读回来时已经少了一段。

这条报告对应的是一个用户环境和一条代码路径，不能据此断定所有 Windows 安装都会出错，尤其不能把社区讨论里的修复候选写成官方版本已经包含的修复。不过它给新手提供了一个很有用的排查方向，如果路径在错误信息里比你选中的路径短，先检查路径读取，不要马上重装 Node.js、修改模型配置或重建工作区。

## 你选了完整路径，DSH 收到的却少了两个字

DSH 的目录选择器会调用 Windows 原生文件夹对话框，系统把用户选中的目录交给底层接口，程序再把这段原生内存转换成 JavaScript 字符串，后面才会拿这条路径创建工作区。

这几个动作发生在同一个功能里，所以错误看起来像`选择文件夹失败`，但实际可能停在更早的一步。对新手来说，最有价值的线索是把三条路径放在一起比较，对话框里看到的完整路径、你复制出来的完整路径、错误信息里的路径。

如果前两条都包含`安卓开发`，错误信息却只到`安卓`，那就说明文件夹选择器返回的字符串已经被截断。此时继续换工作区名称没有太大帮助，因为工作区还没有开始创建，传给创建逻辑的路径就已经不完整了。

## `开`为什么会让路径提前结束

官方讨论把问题定位到了 `packages/host/directory-picker-native/src/win32-dialog-bindings.ts` 里的 `readUtf16`。这段代码从 Windows 返回的内存中读取 UTF-16 字符串，它每次向前移动两个字节，并把低字节为 `0` 当成字符串结束。

问题在于，UTF-16LE 的一个字符由两个字节组成，正确的 NUL 结束符应当是两个字节都为 `0`，只检查第一个字节会把某些正常汉字误判为结尾。讨论里举的`开`是 `U+5F00`，它在 UTF-16LE 中的两个字节顺序是 `00 5F`，低字节正好是 `00`，于是读取过程在这个字上停住，后面的字符全部丢失。

这也解释了为什么纯英文目录可能一直正常，换成某些中文目录却突然失败。中文路径本身不一定触发问题，只有某个字符的 UTF-16LE 低字节碰到了错误的终止条件，路径越长，越可能把这个字符带进来。

讨论中给出的修复方向很小，把判断改成低字节和高字节同时为零即可避免这类提前结束，另外还提到代码把读取范围固定为 32 KB，超长路径也应该有边界处理。后续评论里有人提供了带测试的修复候选分支，但那仍然是社区候选，不能当成 DeepSeek 官方仓库已经合并或 npm 包已经发布的依据。

## 没有 Windows 也可以先做一次离线回归

我在 dsh-learn 里加了一个 `win32-path-doctor`，它不启动 DSH，不加载 `koffi`，不访问网络，也不读取 API Key，只把官方代码里的两种 UTF-16 结束判断放到本地内存夹具中比较。

在 dsh-learn 根目录运行下面的命令

```bash
node scripts/win32-path-doctor.mjs
```

默认夹具使用 C 盘下的 `Users\\XIAOPAN\\Desktop\\安卓开发`，会打印一组对照结果。故意采用旧判断时，结果会停在 `Users\\XIAOPAN\\Desktop\\安卓`，使用两个字节同时为零的判断时，结果会保留完整路径，随后终端会出现下面几行。

```text
PASS 正确的 UTF-16 NUL 判定保留完整路径
PASS 检出低字节为 0 时的提前截断风险
LOCAL_ONLY 不访问 Windows、网络、模型或 API Key，这是对官方 readUtf16 逻辑的离线回归
```

这三行分别对应完整路径、风险检测和无外部调用边界。

你也可以换一个自己的路径样例，命令行参数只作为测试输入，不会修改任何文件

```bash
node scripts/win32-path-doctor.mjs --path 工作区/项目/开发
```

命令输出里的 `CORRECT_UTF16_RESULT` 应当保留完整的中文路径。

这个检查器验证的是字符串读取逻辑，不会代替你电脑上的 DSH Web UI。它能回答`这类 UTF-16 判断会不会把路径截断`，也不能回答当前安装的 DSH 是否已经包含修复、Windows 原生对话框能不能打开、工作区权限是否足够。这几个结果要分开保存，离线回归通过不等于完整运行环境通过。

如果你要检查 dsh-learn 自带的验证脚本，可以运行下面的命令

```bash
node scripts/validate-win32-path-doctor.mjs
```

它会检查正确和错误两种判断、一个中文自定义路径，以及脚本没有读取模型凭据的边界。整个过程不需要 API Key，也不需要网络。

## Windows 新手现在应该怎么处理

遇到工作区路径错误时，先把目录暂时放到一个短的纯英文路径，例如 `dsh-workspace`，确认 DSH 本身能够创建工作区，再把中文路径问题单独记录下来。这样做不代表中文目录不能用，目的是把`工作区权限或安装问题`和`原生路径读取问题`拆开，避免几种故障互相遮住。

如果英文路径可以创建，而包含中文的路径在错误信息里少字，先运行上面的离线检查，再把这些信息放到 Discussion 或自己的排错记录里，Windows 版本、DSH 版本、Node.js 版本、完整选择路径、错误里实际收到的路径，以及是否只在某几个汉字出现截断。路径里可能包含个人目录名，公开前应当换成示例路径，不要把真实用户名和工作项目一并贴出去。

如果你准备从源码验证修复，先固定 DSH 仓库 commit 和本地包版本，检查 `readUtf16` 的终止判断，再在 Windows 上用含`开`或其他中文字符的目录做一次工作区创建。只在英文路径上验证成功，不能证明这个问题已经解决，只在本地字符串夹具里通过，也不能替代真实的 Windows 原生对话框测试。

在 Windows 复测时，目录名可以只改一个字符，这样更容易看出是哪一个码元触发了截断。比如保留同一层目录，把`安卓开发`换成纯英文名称，再把它换回含`开`的名称，两个工作区的权限、上级目录和 DSH 配置都不变，比较结果会比随意换一整条路径更有用。

错误信息也值得原样记录一份，但公开时要把用户名、项目名和公司目录换成示例值。需要保留的是路径长度有没有变化、截断发生在哪个字符、英文路径是否能创建，以及同一个 DSH 版本在两种路径下是否表现不同，这些信息足够帮助别人判断问题停在路径读取还是工作区创建。

如果本地 doctor 能复现截断，源码检查又看到低字节单独作为结束条件，就可以把这两项放在同一条记录里，后续升级 DSH 时重新运行一次。升级后即使错误消失，也要记下新版本和新的输出，因为旧的离线结果只对应那段代码，不能替代新版本的复测。

这份事实卡把一个很像`路径不存在`的错误，拆成了路径选择、UTF-16 转换、工作区创建三个位置。完全新手不必先理解 COM、koffi 或 Windows ABI，先看错误路径有没有被截断，再用本地夹具判断是否命中这类风险，后面的版本复测才有明确位置。

截至这张卡的基线，官方仓库固定 commit `47f943859bef60e4160492346772ded9b24f765a` 中仍能看到这段 `readUtf16` 实现，仓库里的目录选择器包版本为 `0.1.0-rc.5`。DSH 处于快速迭代阶段，后续版本可能改变实现，升级以后要重新检查源代码和 Windows 实测结果，不能只看旧文章里的结论。
